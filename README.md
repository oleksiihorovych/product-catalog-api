# Product Catalog API

An ASP.NET Core API with a layered architecture, targeting .NET 10 LTS.

## Prerequisites

- .NET SDK 10.0.402 (the version is pinned in `global.json`; newer patches in the same feature band are accepted).
- An editor with .NET support, such as Visual Studio Code.

## Structure

```text
src/
  ProductCatalog.Domain/          Domain model and rules
  ProductCatalog.Application/     Use cases and boundary contracts
  ProductCatalog.Infrastructure/  Persistence and external adapters
  ProductCatalog.Api/             HTTP host and dependency composition
tests/
  ProductCatalog.Api.Tests/       In-process HTTP integration tests
```

Application references Domain. Infrastructure references Application and Domain.
Api references Application and Infrastructure for composition. The library
projects are intentionally empty until the first functional slice needs them.

## Build

Run these commands from the repository root:

```sh
dotnet restore
dotnet build --no-restore
```

## Run

```sh
dotnet run --project src/ProductCatalog.Api --launch-profile http
```

The host listens on `http://localhost:5080`. Product endpoints are not implemented
yet. No database, containers, or message brokers are needed to start the host.

| URL | Expected result |
| --- | --- |
| `/health/live` | `200 OK`, text `Healthy`; process liveness only, not dependency readiness |
| `/swagger` | Swagger UI in Development |
| `/openapi/v1.json` | Generated OpenAPI document in Development |
| `/does-not-exist` | `404 Not Found`, `application/problem+json` with a trace identifier |

The HTTP launch profile sets Development. Outside Development, documentation is
disabled and liveness remains available. Configure `AllowedHosts` before exposing
the API under another hostname; local defaults allow only loopback hostnames.
The local HTTP profile requires no development certificate. Use HTTPS termination
and appropriate host configuration when a deployment target is introduced.

OpenAPI is generated by `Microsoft.AspNetCore.OpenApi`; NSwag supplies only the
bundled Swagger UI and its assets. Documentation does not depend on a public CDN.
The document intentionally has no product operations until their slices are implemented.

Errors are returned as Problem Details with a trace identifier. Unexpected errors
never expose exception messages or stack traces in HTTP responses, including in
Development. Full exception diagnostics remain in server logs.

## Tests

```sh
dotnet test
```

HTTP integration tests use xUnit and `WebApplicationFactory`; no external services
are needed. The test-only failure controller is registered by the test host and
is not shipped as an application endpoint. Package versions are centrally pinned
in `Directory.Packages.props`; committed NuGet lock files pin transitive dependencies.

## Bootstrap human verification

From the feature branch, run:

```sh
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
dotnet test --no-build --configuration Release
dotnet run --project src/ProductCatalog.Api --launch-profile http
```

- Open `http://localhost:5080/health/live`: expect `200` and `Healthy`.
- Open `http://localhost:5080/swagger`: expect a working Swagger UI. No product
  operations are expected at this bootstrap stage.
- Open `http://localhost:5080/openapi/v1.json`: expect an OpenAPI 3.x document.
- Request `/does-not-exist`: expect a `404` Problem Details body with `traceId`.
- Request `/__test/failure`: expect `404`; the exception test endpoint is not
  part of the application.
- Stop with Ctrl+C. Nothing needs resetting: bootstrap creates no database or seed.

The same requests are collected in `ProductCatalog.http`. Test results cover
startup, error responses, documentation visibility and test-only route isolation.
Changes are reviewed through a feature-branch PR to `main`. Bootstrap awaits human
verification; the first product slice is a separate PR after approval.
