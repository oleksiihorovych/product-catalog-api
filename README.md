# Product Catalog API

A .NET 10 LTS product catalog with Domain, Application, Infrastructure and API layers.
Bootstrap T0 is accepted. S1 adds full catalog listing; lookup, updates and v2 pagination follow in separate slices.

## Prerequisites and quick start

Use .NET SDK 10.0.402 (pinned in `global.json`; newer patches in the same feature band are accepted).
Run from the repository root:

```sh
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
dotnet test --no-build --configuration Release
dotnet run --project src/ProductCatalog.Api --launch-profile http
```

The IDE-friendly default is **Mock**: no SQL Server, Docker or message brokers are required.
Open `http://localhost:5080/swagger` and run `GET /api/v1/products`.
`ProductCatalog.http` provides executable manual requests.

| Route | Result |
| --- | --- |
| `GET /api/v1/products` | `200`, complete JSON array ordered by ID; `[]` for an empty catalog |
| `/health/live` | `200 Healthy`, process liveness independent of SQL and brokers |
| `/swagger` | Bundled Swagger UI in Development |
| `/openapi/v1.json` | Built-in OpenAPI v1 document in Development |
| `/does-not-exist` | `404` Problem Details with `traceId` |

Swagger and OpenAPI are disabled outside Development. NSwag supplies only the local UI/assets;
OpenAPI is generated by ASP.NET Core. Configure `AllowedHosts` for any non-loopback deployment;
use HTTPS termination at the eventual hosting boundary. No cloud deployment is implemented yet.

## Full-list contract and model

v1 returns every available product in one normal `200 OK` JSON array. It has no pagination,
hidden cap, export job or broker dependency; `page`/`pageSize` query parameters do not truncate it.
The five fields are `id`, `name`, `imgUri`, `price` and nullable `description`.

Implementation choices: positive signed 64-bit IDs; nonblank names up to 200 characters;
absolute HTTP/HTTPS image URIs up to 2048 characters; nonnegative decimal(18,2) prices;
descriptions up to 4000 characters. Prices remain JSON numbers. IDs above JavaScript's safe
integer range require a client capable of preserving 64-bit JSON numbers.

The 23 deterministic demo products have IDs 1–23, names `Demo product 01` through
`Demo product 23`, image URIs `https://example.com/products/{id}.jpg`, and price `id * 10.25`.
Every third description is null; the others are `Description for demo product {id:00}.`.
The last product has ID 23 and price 235.75. Image URIs are sample data; fetching them is not required.

## Storage and SQL setup

Set `Storage__Mode=Mock` or `Storage__Mode=SqlServer`. Unknown modes fail startup.
SqlServer requires `ConnectionStrings__Catalog`, supplied outside Git. No connection string
or password is checked in. For local development, configure credentials through your shell,
another external configuration provider. Do not paste secrets into PRs/logs.

SQL Server Linux containers are officially supported on x64 hosts. ARM64 users should use Mock
locally and a remote x64 SQL Server for database mode; database verification requires an available SQL Server instance.
Emulated SQL Server is not a supported deployment or verification target.

For a dedicated development database, set `Storage__Mode=SqlServer` and
`ConnectionStrings__Catalog` to an administrative connection, then run explicitly:

```sh
dotnet run --project src/ProductCatalog.Api --no-launch-profile -- --migrate --seed
```

This command creates/applies migrations, enables READ_COMMITTED_SNAPSHOT and inserts missing
demo IDs. It exits without serving HTTP. Repeating it does not overwrite existing rows or
add duplicates. On a fresh separate database, omit `--seed` to test an empty catalog.
Never clear an existing database just to demonstrate empty results.

Start the API with a separate runtime connection limited to SELECT on `dbo.Products`:

```sh
dotnet run --project src/ProductCatalog.Api --launch-profile http
```

HTTP startup never migrates or seeds. Schema changes require the administrative command;
the runtime user does not need DDL permissions. The initial migration enables statement-level
snapshot reads and does not force-disconnect existing sessions. Schedule it without competing
connections. Backups and change review are required before applying it to any existing environment.

For a local SQL connection, use encryption; `TrustServerCertificate=true` is acceptable only
for an explicitly trusted development server with a self-signed certificate. Production needs
validated certificates. Configure `Max Pool Size` to fit the per-replica connection budget;
a starting development example is 32, with `ConnectRetryCount=0`.

Migration tooling is pinned in `dotnet-tools.json`:

```sh
dotnet tool restore
dotnet ef migrations list --project src/ProductCatalog.Infrastructure --startup-project src/ProductCatalog.Api
```

## Streaming and failure behavior

SQL uses one ordered, scalar projection, no tracking and no full-catalog materialization.
The clustered primary key supports ID ordering; no redundant index is added.
Retry-on-failure is deliberately disabled on this read path because EF can otherwise buffer
all rows. Statement-level snapshot consistency depends on the migration's database setting;
this is one read, not a cross-request snapshot or a cache.

The API fetches the first row before sending success headers. It flushes the first item promptly,
then batches of 32 and the final array terminator. Backpressure and cancellation reach the reader;
disposal closes its SQL connection. Errors before the response starts return safe Problem Details.
Errors after it starts are logged and abort the transfer: clients must reject an incomplete JSON
array and must not treat a received 200 header alone as a successful full transfer.

`Catalog__MaxConcurrentListings` defaults to 4 per API process (valid range 1–128), with no waiting
queue. Excess listings receive `429` Problem Details before reading storage. This limit is not a
cluster-wide quota or a demonstrated capacity figure. Liveness bypasses it. SQL command timeout
is 120 seconds; proxy timeouts/buffering and slow clients must be evaluated on the target host.
Responses use `Cache-Control: no-store`.

Unexpected exceptions do not expose stack traces or exception messages in HTTP responses.
Full exception diagnostics remain in server logs. Authentication for writes is introduced with
the write slice; this read endpoint is public.

## Tests

The main solution contains fast domain and HTTP tests with xUnit/WebApplicationFactory.
They cover exact listing membership/order, null/decimal values, empty results, unpaginated v1,
initial and mid-stream failures, cancellation/disposal, admission control and bootstrap behavior.
A synthetic 50,000-row stream with 2048-character descriptions is consumed incrementally and
checks sampled live managed heap growth against a generous 64 MiB regression budget. It is
not a process-RSS bound, SQL benchmark or proof of the future 10k-RPS target.

The SQL integration project is intentionally outside the default solution so ordinary IDE/test
runs require no external services. It fails clearly if explicitly run without `CATALOG_TEST_SQL`.
Point that variable at a dedicated x64 test SQL Server with database-create/drop permissions.
Each test creates a unique `CatalogTests_*` database and deletes only its own database:

```sh
dotnet restore tests/ProductCatalog.SqlServer.Tests/ProductCatalog.SqlServer.Tests.csproj --locked-mode
dotnet build tests/ProductCatalog.SqlServer.Tests/ProductCatalog.SqlServer.Tests.csproj --no-restore --configuration Release
dotnet test tests/ProductCatalog.SqlServer.Tests/ProductCatalog.SqlServer.Tests.csproj --no-build --configuration Release
```

SQL checks cover migrations/snapshot configuration, empty HTTP results, repeatable seed and
mock/SQL parity, one untracked query, decimal/Unicode round trips, committed reads, cancellation
closing connections and reads not blocking behind uncommitted writers. EF InMemory is not used
as a substitute for SQL Server.

## S1 human verification

- Start Mock mode using the quick-start commands; open Swagger and execute the v1 listing.
- Confirm a JSON array of 23 unique products ordered 1–23, including ID 23 with price 235.75.
- Confirm all five fields are present and every third description is null.
- Repeat with `?page=1&pageSize=10`: all 23 products must still be returned.
- On a dedicated SQL Server database, explicitly migrate/seed and repeat in SqlServer mode.
- Repeat the seed command and confirm there are still exactly 23 products on the unchanged demo database.
- Use another fresh database migrated without seed: listing returns `200` and `[]`.
- Confirm `/health/live`, local Swagger and unknown-route Problem Details still work.
- Stop the API with Ctrl+C; do not delete existing SQL data for cleanup.

S1 awaits human verification through its feature-branch PR to `main`. Do not merge or start S2
until explicit user acceptance/authorization. Hosting and the RabbitMQ scenario remain deferred.
